# وصلة — نقل الملفات مباشرة

موقع ثابت يعمل عبر GitHub Pages، ينشئ جلسة مؤقتة بين المرسل والمستقبل باستخدام PeerJS Cloud وWebRTC DataChannel.

## التشغيل
1. افتح الموقع من HTTPS.
2. على جهاز المرسل اختر **إنشاء جلسة ورابط**.
3. شارك الرابط أو رمز QR مع الجهاز المستقبل.
4. افتح الرابط على الجهاز المستقبل أو أدخل الرمز في تبويب الاستقبال.
5. بعد اتصال الجهاز، اختر الملفات واضغط إرسال.

## البنية
- `index.html`: الواجهة العربية/الإنجليزية.
- `styles.css`: التصميم المتجاوب ودعم لوحة المفاتيح والريموت.
- `app.js`: إدارة جلسات PeerJS ونقل الملفات.
- `sw.js`: Service Worker وتحديث ملفات الواجهة.
- `manifest.webmanifest`: إعدادات PWA.

## الخادم
يستخدم الموقع PeerJS Cloud العام على `0.peerjs.com:443`، ولا يحتاج إلى نشر Cloudflare Worker أو إعداد رابط خادم يدوي. تعتمد إتاحة الاتصال على الشبكة وخدمات PeerJS وإعدادات NAT/Firewall لدى الطرفين.

## حدود النسخة
- نقل الملفات يتم على دفعات 64KB مع مراقبة مخزن الإرسال.
- الاستقبال يكتب كل جزء فور وصوله إلى ملف في مجلد يختاره المستخدم عبر File System Access API عند دعمه، أو إلى Origin Private File System (OPFS) كتخزين محلي بديل. لا تُجمع أجزاء الملف كاملة في مصفوفة بالذاكرة.
- عند استخدام OPFS يظهر رابط تنزيل للملف بعد اكتمال الكتابة؛ أما عند اختيار مجلد الجهاز فيُحفظ الملف مباشرة فيه.
- دعم اختيار المجلد يختلف بين المتصفحات. في المتصفحات غير الداعمة يستخدم الموقع OPFS، الذي يخزن على مساحة الجهاز الخاصة بالموقع وليس في مجلد التنزيلات مباشرة. تتوقف إمكانية التخزين على المساحة المتاحة وسياسات المتصفح.
- لا يوجد استكمال تلقائي للنقل بعد انقطاع الاتصال في هذه النسخة.
- لا يوجد ضمان لاتصال مباشر في كل الشبكات؛ قد تحتاج بعض الشبكات إلى TURN relay، وقد لا تسمح سياسات الشبكة بالاتصال.
- لا تغلق الصفحة أو تضع المتصفح في وضع توفير الطاقة أثناء النقل.

## النشر
المستودع مهيأ للنشر من GitHub Pages عبر الفرع `main` ومجلد الجذر. بعد دفع التغييرات انتظر اكتمال Pages deployment، ثم حدّث الصفحة تحديثًا كاملاً.

## الاتصال المحلي التلقائي عبر Wi-Fi
أُضيف تبويب مستقل لاكتشاف المتصفحات المفتوحة على نفس عنوان IP العام عبر خدمة WebSocket وسيطة، ثم تنسيق WebRTC SDP. لا يمر محتوى الملفات عبر خدمة الإشارات؛ النقل يكون عبر DataChannel مباشر إذا نجح ICE.

### نشر خدمة الاكتشاف (مرة واحدة)
1. أنشئ حسابًا في Cloudflare وثبّت Node.js وWrangler على جهاز التطوير.
2. من جذر المستودع نفّذ: `npx wrangler login`.
3. نفّذ: `npx wrangler deploy` لنشر `worker/discovery.js` باستخدام `wrangler.toml`.
4. سيظهر عنوان مثل `https://wasla-discovery.<account>.workers.dev`. أدخله في تبويب **الاتصال المحلي**؛ يحوّله الموقع تلقائيًا إلى WebSocket ويحتفظ به على الجهاز.
5. افتح الموقع على الجهازين، واتصل بخدمة الاكتشاف على كليهما، ثم اختر الجهاز الظاهر في القائمة.

### حدود الاكتشاف والخصوصية
- التجميع يتم حسب عنوان IP العام الذي تراه Cloudflare، وليس عبر مسح شبكة Wi-Fi الداخلية. لذلك قد تظهر أجهزة أخرى خلف NAT نفسه، وقد لا تظهر أجهزة على شبكات معزولة أو عبر شبكات جوال مختلفة.
- خدمة الإشارات ترى عنوان IP العام وتعرض اسم الجهاز ونوعه للأجهزة التي تشارك العنوان نفسه. لا تُرسل الملفات إليها.
- WebRTC يستخدم STUN للمساعدة في إنشاء المسار. لا يوجد TURN relay مضمن في هذا الإصدار؛ بعض الشبكات أو متصفحات التلفاز قد تمنع الاتصال المباشر.
- يلزم الإنترنت للوصول إلى الموقع وخدمة الإشارات في الإعداد الحالي، لكن بيانات الملفات لا تمر بالخادم عندما ينجح اتصال WebRTC المباشر.
- رابط Worker يجب نشره وضبطه مرة واحدة على كل جهاز؛ لا يمكن للموقع الثابت اكتشاف عنوان خدمة غير منشورة من تلقاء نفسه.
